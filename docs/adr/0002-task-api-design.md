# ADR 0002: Task API Design

**Status:** Accepted
**Date:** 2026-10-03

## Context

Phase 2 adds the first persistent API surface: submitting tasks and
retrieving them. We need to decide the shape of the request/response
contracts, the layering, and the storage schema.

## Decisions

### 1. UUID primary keys (not integer)
Integer IDs create coordination pressure in distributed systems and leak
information (competitors can count tasks). UUIDs are globally unique
without a coordinator.

### 2. Timezone-aware timestamps
All timestamps are `TIMESTAMPTZ` in Postgres. Naive datetimes cause bugs
across clock skew, DST, and multi-region deployments. There is no
scenario in which a distributed system should store naive timestamps.

### 3. Server-side defaults for created_at / updated_at
The database sets these, not the application. Two app servers with
slightly different clocks still produce consistent timestamps.

### 4. Native Postgres enum for task_status
The DB itself rejects invalid states. This is a stronger guarantee than
application-level validation alone.

### 5. JSONB for payload and result
Arbitrary, schema-less task data without requiring migrations. Queryable
and indexable if needed later.

### 6. Explicit `values_callable` on the enum
SQLAlchemy's default is to store enum *names* (`PENDING`), but our Python
enum uses lowercase *values* (`pending`). Without the override, the DB
and API disagree about the value, causing silent query failures.

### 7. Three-layer separation: schemas / services / routes
- `schemas/` — HTTP boundary (validation, serialization)
- `services/` — business logic, no FastAPI imports
- `api/` — thin HTTP glue

This looks like overkill for 3 endpoints, but Phases 4+ add retry
policies, state machines, and idempotency logic that has nothing to do
with HTTP. Keeping HTTP out of the business layer now means zero
refactoring later.

### 8. Session-per-request via `get_db` dependency
Commit on success, rollback on exception. Services never commit.
The request boundary owns the transaction lifecycle.

## Consequences

- Migration files are generated by Alembic; we review every one before
  applying and never hand-edit them.
- The `tasks` table has three indexes serving the two most common queries:
  list all (by created_at desc), and filter by status.
- API accepts any `type` string for now. The whitelist of executable
  task types will be enforced by the worker in Phase 3 — that is where
  the safety boundary belongs.
